The product we are finishing

Simple mode: the user describes a game, sees progress, plays a working preview, requests revisions, saves the editable project, and exports or shares the result. They should not need to manipulate components, understand JSON actions, or repeatedly prompt the AI to continue.

Pro mode: the same project opens in a full editor with hierarchy, inspector, assets, scripts and advanced authoring tools. Manual development and AI assistance use the same commands and runtime.

Primary success criterion

A supported prompt produces a coherent playable game with a defined objective, suitable controls, feedback, restart and a verified portable export. The workflow stops when its completion contract passes or reports a concrete blocker; it does not stop merely because a few entities were spawned.

Reliability first

Protect user work, make edits reversible, and ensure preview matches delivery.

Depth before breadth

Finish a smaller certified toolset before expanding the behavior count.

Finite automation

Persist tasks, budgets and evidence; avoid endless retries and invented success.

The complete prompt-to-game workflow

1 · Understand2 · Plan3 · Greybox4 · Gameplay5 · Test & repair6 · Polish7 · Verify export8 · Deliver
  1. Understand: infer sensible defaults, clarify only essential ambiguity, and save the Game Brief plus supported scope.
  2. Plan: create a finite task graph and acceptance checklist. Verify tool and asset feasibility before changing the scene.
  3. Build a greybox: establish scale, floor/layout, player, camera, controls and a playable loop before decorative assets.
  4. Implement gameplay: wire objectives, enemies/interactions, score/health, progression, win/fail or endless-loop rules, help and restart.
  5. Test and repair: run the game, simulate inputs, inspect errors and outcomes, and repair failed checks within a fixed budget.
  6. Polish: apply consistent assets, animation, lighting, HUD, sound and performance improvements without breaking the verified loop.
  7. Verify delivery: save a checkpoint, package assets, run the exported artifact in a clean environment, and repeat required gameplay checks.
  8. Deliver: show a truthful completion report and playable preview. Offer export or authorized publishing. Persist the run so subsequent requests modify the existing game.
Example completion contract: island adventure

The player spawns safely, movement and camera work, exactly five reachable crystals can be collected once each, the HUD counts progress, the escape stays locked until collection is complete, the escape triggers victory, restart resets the run, the saved project reopens correctly, and the exported game passes the same checks. Art quality and performance are assessed against a declared target.

A revision prompt uses the same loop at smaller scope. “Make it nighttime and add two guards” becomes a change plan, checkpoint, scoped edit, regression check and updated preview—not a fresh world that discards existing work.

Suggested boundaries: introduce focused project/persistence, validated commands, shared runtime, workflow orchestration, validation and export modules. Keep UI rendering separate from state mutation. Extract incrementally from existing files rather than rewriting the entire editor in one step.

Provider access: use a narrow platform adapter. Desktop can broker credentials in the main process; web needs a deliberate local/BYOK or backend design. Never ship a shared service secret in frontend code. Generated game scripts execute outside the credential-bearing editor context.

What “finished” means for the first dependable release

Required

  • Trustworthy save/open/recovery and reversible edits.
  • Simple chat + preview and usable Pro mode.
  • Three complete supported single-player game families.
  • Persistent AI build/test/repair workflow.
  • Portable verified exports.
  • Truthful status and tested supported platforms.

Conditional / separate service

  • Real public hosting requires a functioning hosting service.
  • Single-file HTML requires a compatible embedding strategy.
  • Mobile claims require touch and device validation.
  • Windows/macOS require tested builds.

Defer until stable

  • Multiplayer, collaborative editing and accounts beyond hosting needs.
  • Large open worlds and unrestricted genre coverage.
  • New advanced behavior batches.
  • Asset marketplaces, generative 3D services and elaborate agent visualizations.

A release may omit hosting or advanced graphs if those controls and claims are removed or clearly experimental. It may not omit project safety, truthful completion, or functioning gameplay/export for its declared supported scope.

P0 · Establish the truth & secure the foundation

Critical · first

Dependencies: None. This phase must precede wider distribution and credential-bearing automated execution.

P0.1Create a verified capability register Baseline inventory completed · certification pending

Inventory every menu, behavior, AI action, graph tool, asset workflow, and export feature. Classify each as working, partial, experimental, broken, or absent. Record editor support, save/load support, runtime support, export support, tests, and user-visible claims separately. A catalog entry or notification is not evidence of a working mechanic.

P0.2Close the credential exposure path Completed · 31 October 2026

Restrict development services to loopback by default. Remove the network-accessible credential-return endpoint or replace it with an authenticated, origin-checked local broker. Keep desktop credential access scoped to the trusted application. Never include credentials in project packages, games, logs, or diagnostics.

P0.3Treat AI output and imported projects as untrusted In progress · rendering/navigation completed

Render AI text safely; sanitize any supported rich text. Validate imported documents, action payloads, asset locations, and external URLs. Isolate generated game code from the editor and its credentials. Restrict Electron navigation and external-link protocols; define a production content-security policy.

P0.4Establish a reproducible baseline

Pin the renderer/runtime dependency versions through the lockfile and export manifest. Record build commands and supported targets. Separate ignored generated output from source. Add editor-focused CI for tests, production build, schema checks, and representative export checks; the cloned engine’s CI is not a substitute.

P0.5Make product claims accurate

Remove false success messages for publishing, skill consultation, and incomplete mechanics. Clearly label experimental tools. Replace unsupported AAA, universal offline, and autonomous-completion claims with tested capabilities.

Exit gate

Credential endpoints cannot be reached from another machine; hostile AI text is rendered inert; no secret enters a saved/exported artifact; capability register and reproducible editor checks exist.

Critical · foundation

Dependencies: P0 security, baseline and capability inventory.

P1.1Introduce a versioned project document Version 1 foundation completed · full reference migration pending

Define project ID, schema version, engine version, project settings, scenes with stable IDs, active scene ID, asset manifest, scripts and attachments, materials, prefabs, animation data, timeline data, HUD, triggers, input mappings, and supported graph definitions. Store references by stable ID rather than display name. Design migration and validation before adopting the format.

P1.2Build complete serialization and restoration Scenes / scripts / transforms / collision / terrain / declared audio slices completed · full coverage pending

Save and restore all component fields, collision extents, materials and textures, sound sources/slots, script definitions and bindings, terrain mesh/generation data, animation tracks, custom properties, and behavior configuration. Use local transforms for hierarchy reconstruction. Avoid serializing imported model subtrees twice. Await asset loading and report failures before declaring a project open.

P1.3Create a real project package JSON Save/Open and declared-asset embedding delivered · full archives/runtime pending

Provide a native editable package containing the project manifest and required assets. Preserve every scene and portable references. Include licensing/attribution metadata. Support browser file import/download and a desktop save adapter without assuming browser access to arbitrary local files.

P1.4Add autosave, recovery and revisions Local IndexedDB history / file state / restore completed · native saves and full revisions pending

Create rolling local recovery snapshots, a visible saved/unsaved state, save failures, crash recovery, and checkpoints before AI builds or project migrations. Browser storage needs quota handling; desktop saves need atomic replacement and backup. Distinguish a recovery snapshot from an explicitly saved portable project.

P1.5Clean scene lifecycle and ownership Scene switching / stale behavior cleanup improved · full resource lifecycle pending

Destroy or release removed entities and owned GPU/audio resources, unregister stale behaviors and triggers, clear scene-specific selection/history appropriately, and prevent duplicate assets/listeners on reopening. Make scene rename, duplicate, switch, and delete consistent and ID-safe.

P1.6Prove lossless round trips Foundation regression fixtures pass · full resource fixtures pending

Build fixtures with nested transformed entities, multiple scenes, imported animated models, scripts, prefabs, physics, textures, sound, terrain, HUD, and graphs. Compare meaningful state before save and after reopening. Exercise missing assets, corrupted input, old formats, storage exhaustion, and interrupted writes.

Exit gate

A representative multi-scene project reopens after application restart with equivalent content and behavior, all scripts restored, portable assets intact, and a usable recovery snapshot after interruption.

P2 · Unify editing operations & isolate play sessions

Critical · foundation

Dependencies: P1 project identity, snapshots and deterministic loading.

P2.1Use one command and validation layer

Route UI edits, AI changes, scripting attachments, materials, behaviors, HUD, atmosphere, graphs, and scene operations through typed validated commands. Use the same argument rules for manual and AI actions. Reject unsupported component configurations rather than silently creating fake component objects.

P2.2Make AI batches reversible transactions

Group one requested change into a named transaction with preconditions, before/after state, an action journal, resource ownership, and rollback. Await asynchronous model/texture loads before marking commands complete. Handle cancellation, partial failure, and redo deterministically. Undo one prompt as one coherent operation.

P2.3Create an isolated game session Disposable-copy restoration completed · separate context pending

Run a clone/snapshot of project content in a separate preview context; exclude editor helpers and credentials. Initialize physics explicitly. Start with the configured game camera and input map. Stop destroys session resources and returns to the exact editing state. Provide explicit optional apply-back only for supported changes.

P2.4Share the game runtime

Extract shared scene loading, asset resolution, gameplay behaviors, scripts, HUD, physics, animation, and environment application from the exporter/editor. Preview and exported games must consume the same versioned runtime and project representation. Do not maintain two unrelated behavior implementations.

P2.5Make runtime failures visible

Collect structured errors, warnings, missing references, physics failures, script faults, loading timings, and session events. Link actionable issues to the affected object or script. Keep diagnostics free of secrets and cap log volume.

Exit gate

One undo restores an entire mixed AI edit; failed asynchronous batches roll back; play/stop leaves the editing project unchanged; the same fixture behaves consistently in preview and export.

P3 · Deliver the new Simple mode

High · core product experience

Dependencies: P1/P2 save, rollback and preview foundations. UI design can begin earlier; acceptance requires those foundations.

P3.1Replace the dense editor layout

Give Simple mode two main areas: conversation and a large playable preview. Keep New/Open, Save, project name/save state, Play/Stop or Restart, Export/Share, and a small settings menu. Put build status, cancellation and checkpoints where users can find them. Use plain language throughout.

P3.2Move technical tools into Pro mode

Hide hierarchy, component inspector, asset browser, transform toolstrip, terrain/material/shader/flow graph tools, animation panels, physics tools, timeline, profiler, and developer console from the default Simple layout. Keep the underlying project model intact. Offer an explicit Open in Pro action and a return to Simple action without conversion or data loss.

P3.3Make the conversation task-oriented

Show the game brief, short assumptions, next milestone, active task, preview-ready checkpoints, and concise summaries of completed changes. Provide example prompts and contextual suggestions such as add an enemy, improve lighting, make controls easier, or create another level. Keep raw JSON, stack traces and agent chatter in optional details.

P3.4Handle first-run and empty states

Let users start from a prompt, a small set of tested genre templates, or an existing project. Detect missing AI configuration and offer setup without discarding the prompt. Use sensible defaults for camera, controls, difficulty, visual direction, and desktop/mobile target. Ask only questions that materially affect feasibility or design.

P3.5Design interruptions and error recovery

Users can cancel the current build, keep the last working preview, revert a change, resume later, or retry a failed step. Clearly distinguish planning, building, testing, repairing, paused, blocked, ready to preview, and finished. No fake progress percentage or unconditional success banner.

P3.6Validate usability and accessibility

Provide keyboard access, focus handling, readable contrast, responsive panels and clear loading states. Test the flow on smaller laptops. Confirm a novice can create, revise, save, reopen, play and export a supported game without touching the Pro interface.

Exit gate

A first-time user completes the supported prompt-to-export journey through chat and preview only; mode switching preserves the same project, selection context where relevant, and build history.

P4 · Define a complete game before generating content

High · automation contract

Dependencies: P0 capability register and P1 persisted project metadata; uses P3 conversation design.

P4.1Turn the prompt into a persisted Game Brief

Capture genre, audience, platform/input, visual style, camera, core loop, objective, fail condition, progression, number of levels, session length, asset constraints, performance target, accessibility and content constraints. Store explicit user requests separately from inferred defaults. Let users edit the brief.

P4.2Create a testable completion contract

Every supported game needs a playable entry point, controls/help, functioning core mechanic, feedback/HUD, objective, win/lose or an explicitly intended endless loop, restart, sound policy, saved project, and verified export. Define optional features separately so the agent cannot endlessly expand the scope.

P4.3Plan a dependency graph of tasks

Generate milestones and tasks with stable IDs, dependencies, required capabilities, target objects, inputs, expected changes, acceptance checks, estimated cost class, and rollback point. Order a playable greybox before visual polish. Require feasibility validation against the capability register before execution.

P4.4Bound scope and unsupported requests

Start with a deliberately supported set of compact single-player game types. Suggest a feasible alternative when requests require unavailable capabilities. Treat multiplayer, arbitrary AAA-scale worlds, custom engine work and unrestricted code generation as separate future scope. Never silently replace an unsupported mechanic with a sound or notification.

P4.5Plan creative direction and asset use

Choose a coherent palette, scale conventions, lighting, UI style, and an approved asset family. Track attribution, permitted use, download size, triangle/texture budgets, animation availability and fallback assets. Use deterministic procedural assets where appropriate. Missing assets must fail visibly or use a disclosed compatible substitute.

Exit gate

Before building, each supported request has a saved brief, finite task graph, explicit completion checks, known asset strategy, and a feasible supported scope.

P5 · Build a persistent autonomous workflow runner

High · automation engine

Dependencies: P2 transactional tools, P4 task/completion contracts and P1 durable storage.

P5.1Implement a durable state machine

Use explicit states: draft, planning, queued, executing, validating, repairing, checkpointed, awaiting input, paused, cancelled, failed, ready for review, completed. Persist run ID, brief revision, task graph, current step, action journal, evidence, budgets and checkpoint references. Resume safely after restart rather than replaying completed work.

P5.2Expose typed, discoverable tools

Replace fenced-text-only execution with provider tool calling where available and a strictly validated structured fallback. Generate tool schemas and AI documentation from one capability registry. Cover read/query, create/update, asset lookup/import, script lifecycle, run/stop, inspect, test, save/checkpoint, and export. Return structured success, failure and retryable status.

P5.3Provide accurate scene and project context

Let the agent query stable IDs, hierarchy, transforms, components, behaviors, scripts, assets, active scenes, cameras, errors and previous task results. Supply compact summaries and retrieve details as needed. Version context and detect concurrent user changes. Never rely on the last eight chat messages as project memory.

P5.4Make execution safe to repeat

Use idempotency keys and expected revision checks for mutating actions. Prevent duplicate entities/assets on retries. Run changes against checkpoints or working revisions. Validate references before commit, await loads, and record actual results instead of assuming requested actions succeeded.

P5.5Integrate skills as real knowledge

Package curated skill content with the application or retrieve it through a defined loader. Consultation must return instructions and examples to the model. Keep skill versions tied to available tools and runtime behavior. Resolve the current no-op consultation path and avoid shipping unusable filesystem references.

P5.6Implement provider resilience and budgets

Support request timeout, cancellation, rate-limit backoff, bounded retries, context compaction, configurable token budgets and cost visibility where provider data permits. Do not silently change providers or paid accounts. Persist incomplete runs without secrets; credentials remain in the configured secure adapter.

P5.7Replace keyword team mode with real task coordination

Have a planner assign validated tasks to builder, gameplay, art and QA responsibilities. Start with sequential execution against shared project state; parallelize only isolated work when conflict handling is proven. Persist handoffs, inputs, outputs and evidence. Role names do not establish independent reasoning or successful QA.

P5.8Give users reliable control

Pause at safe transaction boundaries, stop model requests, cancel queued tasks, preserve the last known good state, and resume from a checkpoint. Require user input only for missing essentials, external publishing authorization, budget increases or scope changes; ordinary in-scope building should continue automatically.

Exit gate

A supported request continues through multiple dependent tasks without repeated prompts, survives restart, cancels safely, avoids duplicate work on retries, and reports actual task state and remaining blockers.

P6 · Add automated playtesting, inspection & repair

High · prove completion

Dependencies: P2 shared runtime and telemetry, P4 acceptance contracts, P5 persisted runner.

P6.1Validate structure before launching

Check required camera/player or genre equivalents, spawn safety, scripts, asset availability, references, collision/physics prerequisites, scene transitions, HUD bindings, input actions and objective wiring. Report defects with stable object IDs and actionable causes.

P6.2Run real game smoke tests

Launch the shared runtime in an isolated browser test context. Wait for assets and readiness, capture console/runtime failures, simulate input, test restart and scene transitions, and collect screenshots. Use a consistent seed and bounded test duration. A generated HTML string is not a passing playtest.

P6.3Verify mechanics and outcomes

For each supported genre, assert movement/input effect, collisions where needed, damage/collection/scoring, objective progress, fail/win or endless-loop rules, restart state and reachable required content. Use runtime telemetry plus scripted scenarios; screenshots alone cannot establish playability.

P6.4Review presentation and performance

Capture start, gameplay and end-state views. Check camera framing, visible player, readable UI, asset scale, obvious clipping and lighting. Measure load time, frame timing, memory trend, draw calls and asset weight on declared hardware tiers. Visual model review supplements deterministic tests, and does not claim universal artistic correctness.

P6.5Make repairs bounded and evidence-driven

Translate defects into targeted repair tasks, checkpoint, apply changes, rerun failed checks and relevant regressions. Detect repeated failures and no-progress cycles. Default to a configurable maximum of three repair cycles per defect group; then keep the working checkpoint and explain the blocker instead of declaring success.

P6.6Create a completion report

List requested features, checks passed/failed, screenshots, export verification, known limitations and the exact project/runtime revision tested. Only mark completed when required checks pass. Let the user preview intermediate results without confusing them with the finished game.

Exit gate

An intentionally broken supported game is detected and repaired within budget; an unrepairable game reports a specific blocker; no completion state is possible with failing required checks.

P7 · Finish the gameplay & visual authoring foundation

High · focused depth

Dependencies: Begins after P0 inventory; integrates with P1/P2. Certified starters must precede final AI benchmark acceptance.

P7.1Certify a core behavior set

Prioritize movement, camera, physics interaction, health/damage, enemies, pickups, score, checkpoints, doors, hazards, spawning, objectives and restart. Define configuration schemas and interoperable events. Add behavior lifecycle cleanup, reset and serialization. Test combinations rather than attachment alone.

P7.2Finish or withdraw incomplete advanced behaviors

Audit all advertised behaviors. Implement genuine paired portals, surface walking, time control and other advanced mechanics only when they fit the release scope; otherwise label experimental or hide them. Remove fake success notifications. Verify runtime/preview/export parity for every exposed behavior.

P7.3Complete script lifecycle and isolation

Provide script registration, attachment, attributes, initialization/update/cleanup, compilation/runtime error reporting, save/load, and export. Run generated code without editor privilege or credentials. Have AI patch scripts with revision checks and validate them before activating.

P7.4Resolve graph tools honestly

Decide which visual flow, shader and animation graph capabilities ship. Supported graphs need saved node/edge data, schema validation, deterministic execution/compilation, live preview and export parity. A canvas of nodes that does not control runtime behavior must not be offered as a finished blueprint or shader engine.

P7.5Complete reusable content workflows

Support versioned prefabs with stable references, material and texture persistence, terrain persistence, animated asset loading, animation state configuration, sound source/slot restoration and deterministic scene transitions. Make missing-resource diagnostics comprehensible in Simple mode.

P7.6Build tested genre starters

Ship compact third-person collection/adventure, first-person arena, and platformer starters using certified components. Each starter includes menus/help, appropriate input, objectives, failure/restart, HUD, coherent presentation and portable assets. Use these as constrained building blocks, not canned outputs for every prompt.

P7.7Define 2D scope explicitly

For the first release, declare whether platformers are 3D or 2.5D. If native 2D games are included, add orthographic setup, sprites/atlases, 2D input/physics conventions, layered UI and suitable templates as a separate tested workstream. Do not imply every HTML game genre is covered by the 3D toolset.

Exit gate

Every release-visible capability has an explicit support status and passes save/open, preview and export scenarios; all three starters are complete playable games.

P7A · Production asset library

High priority · requested content milestone · planned

The current small collection and block-style characters are not sufficient for the intended product. Deliver a useful preloaded core pack plus optional themed packs, with much better quality and variety and structured AI discovery. Read the detailed asset-library plan, targets, sources and acceptance gates.

Content quality and variety

Plan for 24 rigged humanoids, 30 creatures/enemies, 100 architecture pieces, 60 vegetation/natural props, 120 interactable props, 30 vehicles/equipment items, 50 weapons/items and 100 PBR material sets across the full library. These are acquisition targets, not imported inventory. Curate a compact core of roughly 100–150 models and 25–40 material sets first.

Coherent game-ready packs

Approve stylized adventure and more detailed contemporary/industrial visual families. Normalize scale, pivots, materials, collisions, LODs, rigs and clip coverage. Evaluate assets in actual gameplay views; recolors and promotional screenshots do not establish quality.

AI can find real assets

Stable asset IDs, semantic tags, bounds, biome/style/role, animation metadata, compatibility, costs and dependency manifests. Planning chooses a coherent family and available actions; execution resolves installed IDs instead of inventing model URLs.

  1. A01: audit provenance and visual quality of existing assets; replace weak defaults.
  2. A02–A03: approve style samples and record per-version rights for raw asset redistribution in the studio and game exports.
  3. A04–A05: normalize GLB/texture/rig data and ship actual PBR material sets.
  4. A06–A07: searchable manifests, local thumbnails, animation previews and optional-pack installation.
  5. A08–A09: integrate AI selection/substitution; add procedural or generated content through the same review pipeline.
  6. A10: verify pack/export, memory and load budgets, then ship curated versioned content.

Source policy: evaluate the official Poly Haven and ambientCG asset terms as candidates. The current Quaternius QAL restricts standalone asset redistribution, so it is not an automatic preloading source. Preserve exact per-pack/version evidence and do not assume every free download can be bundled into an editor.

Exit gate

The three reference games use attractive coherent content without manual path repair. Every official asset has reviewed provenance, rights, compatibility metadata, previews, required animation coverage and verified save/open/export. At least 30 representative AI asset searches resolve suitable installed IDs. No new assets have been imported as part of writing this plan.

P8 · Ship portable exports & genuine sharing

High · delivery

Dependencies: P1 asset packaging, P2 shared runtime and P6 delivery checks. Hosting is a separate service dependency.

P8.1Define export targets Embedded HTML runtime completed · archive pending

Support a portable folder/ZIP with a pinned runtime and assets as the reliable baseline. Offer a single embedded HTML option only for assets and sizes the exporter truly supports. Record any remaining network dependency explicitly. Keep editable project packages distinct from playable exports.

P8.2Implement dependency collection Declared media + engine/physics completed · full dependency coverage pending

Traverse every scene, script, model, texture, sound, animation and runtime dependency. Resolve local/blob/remote references into durable packaged locations, include licenses, rewrite URLs, and report missing or disallowed dependencies before completion. Bundle engine and physics consistently with preview.

P8.3Test portability and offline behavior Moved-file offline physics/model fixture passed · full gameplay checks pending

Run the delivered artifact from a clean location with network disabled for offline claims. Test browser file restrictions and provide a clear local-server path for folder exports where required. Verify loading, gameplay, win/lose/restart and scene transitions outside the editor.

P8.4Implement actual publishing

Build or connect a hosting API with authentication, upload progress, project ownership, validation, game revisions, quotas and error handling. Return a public URL only after upload and an independent fetch confirms availability. Support update, unpublish/delete and cache invalidation. Do not use invented public URLs.

P8.5Keep private work private

Local save/export should work without an account or publication. Clearly separate Export from Publish, show what will be uploaded, and preserve user authorization for the specific publishing action. Exclude keys, internal logs, private prompts and editor-only metadata from playable games.

Exit gate

An exported supported game plays on a clean target without editor files; offline claims pass offline tests; publishing returns an actually reachable revision with ownership and removal controls.

P9 · Harden performance, compatibility & desktop delivery

High · release readiness

Dependencies: P3 interface, P5/P6 automation and P8 exported artifacts.

P9.1Declare and test a support matrix

Choose initial desktop/browser targets and minimum GPU/memory requirements. Prioritize Linux desktop and supported Chromium/Firefox browser versions before claiming universal platforms. Add Windows/macOS builds only with real installation and workflow validation.

P9.2Measure and optimize loading

Use dynamic loading for advanced Pro tools and optional modules. Reduce the initial application bundle, avoid loading unnecessary model libraries, cache assets safely, and show real progress. Establish budgets from reference hardware and enforce measured regressions rather than marketing estimates.

P9.3Test mobile exports deliberately

Provide touch controls, responsive HUD, safe-area handling, audio unlock, orientation behavior, memory/texture limits and representative mobile performance. Distinguish mobile-playable exports from a mobile authoring editor; neither is automatic.

P9.4Exercise long sessions and recovery

Repeatedly open/close projects, enter/exit play, import/remove assets, build/cancel AI runs and switch scenes. Check memory/GPU/audio/listener cleanup, input focus, crashes, context loss, offline provider failure and suspended/resumed applications.

P9.5Make releases reproducible

Document development versus packaged launch, enforce artifact contents, verify desktop integrations and clean-machine installation, preserve user projects across updates, and define update/rollback handling. Keep build artifacts out of git; publish binaries through a separate release channel.

P9.6Add actionable support diagnostics

Offer opt-in redacted diagnostic export with app/runtime version, platform, failed task IDs and errors. Explain local storage, AI provider configuration and offline limitations. Add a brief first-game guide matching the finished interface.

Exit gate

The declared support matrix passes installation and end-to-end workflows, repeat-session resource checks, measured performance budgets and interruption/recovery scenarios.

P10 · Prove the product with benchmarks & beta users

Release gate

Dependencies: All preceding release-scope phases. Optional deferred capabilities do not block if removed from release claims and UI.

P10.1Create a fixed prompt benchmark

Use at least 20 supported prompts across the three starter families, including modifications to an existing project. Version prompts, random seeds, asset packs, provider/model settings and expected checks. Include failed provider calls, missing assets, conflicting edits and resume-after-restart cases.

P10.2Measure completion honestly

Track end-to-end completion rate, export success, median and slow-tail duration, repair count, manual interventions, provider cost where measurable and visual/usability feedback. Proposed beta target: at least 18 of 20 supported prompts pass required checks without manual scene repair, with all failures reported accurately. Freeze thresholds before running; report sample size and model variability.

P10.3Run novice and Pro usability sessions

Observe novices using only Simple mode and experienced users using Pro mode. Record abandoned flows, unclear controls, trust in saving/undo, quality of AI changes and successful delivery. Fix blockers before adding optional features. Recruit outside the development workflow so hidden assumptions become visible.

P10.4Close release blockers

Zero known critical credential exposure or project-loss issues. Required checks pass for reference games. No fabricated publishing/completion statuses. Complete recovery, packaging, attribution and accurate release notes. Track deferred features explicitly rather than claiming them as complete.

P10.5Release a scoped version and keep improving

Publish the supported capability list, tested platforms, known limitations, benchmark results and upgrade guidance. Keep a regression corpus from real user failures. Expand genres, advanced mechanics and model support only after the existing completion rate stays stable.

Exit gate

All release gates pass on a tagged candidate, novice users finish the intended workflow, benchmark evidence is retained, and the supported scope matches actual behavior.

How to execute and maintain this roadmap

  • One canonical backlog: create implementation issues using the IDs above. Each issue records scope, owner, dependencies, acceptance checks, evidence links and status: planned, active, blocked, verifying, or done.
  • Done means verified: code, UI integration where needed, persistence, preview/export compatibility, tests and accurate documentation are complete for the task’s declared scope. A file or menu entry alone is insufficient.
  • Review milestone evidence: demonstrate the user journey at every milestone. Record the exact revision and outstanding defects. Do not mark a phase complete because its subtasks were merely drafted.
  • Protect working content: use project fixtures and reference games as regressions. Changes to schema/runtime require migration and compatibility checks.
  • Keep development changes reviewable: use focused commits, run relevant checks, commit and push completed changes according to repository policy. Never commit credentials, dependency folders, generated distributions or binary releases.
  • Update this document: link completed work and measured results, adjust the scope openly, and preserve unresolved risks. Reassess priorities after every milestone rather than adding unchecked features.
Final release checklist
  • Project save/open/recovery and undo are trustworthy.
  • Simple mode delivers the chat-and-preview journey without advanced editing.
  • Pro mode uses the same reliable project, commands and runtime.
  • AI runs persist, continue across tasks, test results and repair within limits.
  • Required game outcomes and restart pass for supported genres.
  • Portable exports run outside the editor; real hosting exists if advertised.
  • No critical known credential exposure or project-loss defects remain.
  • Benchmark, usability, compatibility and performance evidence supports release claims.
